# Ловушка на сервере компании

В разделе «Серверы» нажмите «Подключить сервер»: форма помогает сформировать
команды подключения и назначения, показывает готовность узла. Worker token
выдаёт администратор Swarm; форма не отправляет его в API и не сохраняет.

В конструкторе сети выберите «Где развернуть ловушку» → нужный сервер.
Панель создаст ловушку на выбранном узле, выдаст штатные реквизиты и mTLS-сертификат,
применит профиль и запустит её. Команды, события и восстановление связи используют
существующий протокол. Выбранный сервер сохраняется в `deployment_node_id`.
Недоступный сервер не заменяется другим: ловушка ждёт возвращения своего узла.

## Подключить сервер один раз

Подключение выполняет администратор инфраструктуры. Нужен Linux с Docker Engine
и доступом к общему Swarm через частную сеть или VPN. Компания подключается как
**worker**, без прав manager. Общий Swarm предполагает доверие к администраторам
серверов; это не изоляция взаимно недоверенных клиентов.

Между узлами разрешите TCP 2377 до manager, TCP/UDP 7946 и UDP 4789.
Не открывайте overlay-порт 4789 в публичный интернет.
Основание: [документация Docker](https://docs.docker.com/engine/swarm/swarm-tutorial/).

1. На manager получите команду подключения:

   ```sh
   docker swarm join-token worker
   ```

2. Выполните выданную команду на сервере компании. Используйте адрес manager
   в частной сети, достижимый с нового сервера. Join token является секретом:
   не передавайте его в чат, репозиторий или клиентское API.

3. На manager найдите полный ID нового узла и назначьте его организации:

   ```sh
   docker node ls --no-trunc
   docker node update --label-add honeyforge.organization=ORGANIZATION_UUID NODE_ID
   ```

   UUID организации доступен администратору компании в `GET /api/session`,
   поле `organization.id`. Метку задаёт только администратор Swarm.
   Узлы без корректной метки и manager-узлы в список серверов компании не попадают.
   Не переназначайте сервер другой организации, пока на нём есть её ловушки.

4. До создания ловушки загрузите на новый сервер **те же версии образов**, что
   настроены у оркестратора: `DECOY_TCP_IMAGE`, `DECOY_REDIS_IMAGE`,
   `DECOY_HONEYTOKEN_IMAGE`, `DECOY_SSH_IMAGE`, `SSH_SANDBOX_IMAGE`.
   Для текущих локальных тегов можно использовать архив:

   ```sh
   # На manager; замените теги, если они отличаются от значений по умолчанию.
   docker save -o honeyforge-decoys.tar honeyforge/tcp-decoy:local honeyforge/redis-decoy:local honeyforge/honeytoken-decoy:local honeyforge/ssh-decoy:local honeyforge/ssh-sandbox:local
   # Передайте архив на сервер компании вашим обычным защищённым способом.
   # На сервере компании:
   docker load -i honeyforge-decoys.tar
   ```

   При обновлении версии повторите загрузку на всех используемых workers.
   Supervisor может запускать локальный worker/sandbox с `--pull=never`, поэтому
   одной доступности registry недостаточно: образ должен присутствовать на узле.

5. Дождитесь `Ready / Active` в `docker node ls`. Оркестратор обновляет список
   после очередного цикла, обычно за несколько секунд. В панели выберите сервер.
   Если оркестратор не наблюдал узел 30 секунд, он считается недоступным.

## Сеть, порты и проверка

- Management и decoy overlay-сети должны быть доступны на новом узле. Supervisor
  подключён к management-сети; worker создаётся в decoy-сети на той же машине.
  Проверяйте доступ к `AGENT_WS_URL` и TLS Redis из management-сети нового узла,
  включая DNS-имена и имена в сертификатах. Центральный Redis остаётся журналом
  событий; работа требует его доступности по штатному TLS-соединению.
- Для TCP/Redis/HTTP порт публикуется локальным worker на сервере компании;
  для SSH — Swarm-сервисом в режиме `host`. Открывайте порт приманки на firewall
  компании. Указанный для платформы `DECOY_BIND_IP` не переносится на сервер
  компании: на выбранном worker используется `0.0.0.0`.
- API проверяет конфликты управляемых ловушек на одном выбранном узле, включая
  ожидающие применения конфигурации. Одинаковые порты на разных выбранных узлах
  разрешены. Порты сторонних программ не известны API: они должны быть свободны.
- Ловушки без выбранного узла сохраняют режим платформы и резервируют свои порты
  консервативно для всех узлов. Старые регистрации не переносятся автоматически.
- После создания дождитесь `online / running`, проверьте hostname агента,
  подключитесь к адресу сервера компании на порту профиля и убедитесь, что события
  появились в панели. Затем проверьте «Остановить» и «Запустить».

На manager можно проверить закрепление и состояние:

```sh
docker service inspect node-metrics-TRAP_UUID --format '{{json .Spec.TaskTemplate.Placement.Constraints}}'
docker service ps node-metrics-TRAP_UUID --no-trunc
```

## REST

`GET /api/traps/deployment-nodes` возвращает `{ "items": [...] }` с полями
`id`, `hostname`, `address`, `ready`; только для организации текущей сессии.

```json
{
  "request_id": "UUID",
  "name": "company-dmz",
  "profile_id": "PROFILE_UUID",
  "deployment_node_id": "SWARM_NODE_ID"
}
```

Это тело `POST /api/traps`; остальные требования сессии, Origin и CSRF прежние.
Без `deployment_node_id` новая автоматическая ловушка размещается на manager
платформы. Изменение сервера существующей ловушки не предусмотрено: остановите
и удалите её штатно, затем создайте новую регистрацию.
Неизвестный, чужой или недоступный узел возвращает `409 deployment_node_unavailable`.
Неправильный формат ID — `422 validation_failed`.
