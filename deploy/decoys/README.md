# Автоматическое размещение приманок

Подключение сервера компании и выбор узла в панели: [REMOTE-NODES.md](REMOTE-NODES.md).

Основной `docker-compose.real.yml` собирает образы приманок,
запускает оркестратор и включает автоматическое развертывание в API. Дополнительный
Compose-файл и ручное создание Swarm или сети не нужны.

```sh
docker compose -f docker-compose.real.yml up --build -d
```

Используйте обычные `.env` и сертификат из [REAL-STACK.md](../../REAL-STACK.md).
Оркестратор сам включает одноузловой Docker Swarm, создаёт overlay-сеть и
создаёт отдельные сети `hf-mgmt` и `hf-decoys`. API, Redis и nginx подключаются
только к `hf-mgmt`. После `POST /api/traps` он выдаёт реквизиты агенту,
создаёт Swarm service, ставит команды `apply_config` и `start`. Агент открывает
обычную приманку в отдельном контейнере `hf-decoys`. Приманка открывает порт
из профиля и передаёт события агенту через TLS-pipe; агент использует WSS/Redis
в управляющей сети. Ответ
`POST` остаётся `201`: развертывание асинхронное; состояние видно через
`GET /api/traps/{id}` и `GET /api/traps/{id}/commands`.

Без выбранного узла новые ловушки размещаются на manager платформы. При выборе
сервера компании сервис закрепляется за его worker ID и меткой организации;
на другой узел он не переезжает. Список серверов обновляет оркестратор.
Для TCP/Redis/HTTP каждой ловушке соответствуют доверенный агент с Docker socket
в mgmt-сети и отдельный контейнер приманки без socket. Токен агента,
адрес Redis и сертификат CA передаются через Docker secrets; процесс приманки
работает без доступа к ним. Перед запуском приманки entrypoint запрещает новые
исходящие соединения, затем сбрасывает UID и capabilities. Ошибка настройки
firewall останавливает запуск. Входящие TCP-соединения и ответы на них разрешены.
Локальный Redis из основного Compose хранит журналы
в постоянном томе.

Redis URL должен использовать `rediss://` и содержать `REDIS_PASSWORD`.
Compose требует пароль минимум из 32 hex-символов, включает protected mode
и использует аутентифицированный healthcheck. Для отдельного CA Redis задайте
`AGENT_REDIS_CA_FILE` оркестратору; иначе агент использует `AGENT_CA_FILE`.
Телеметрия защищена TLS и при передаче через overlay-сеть между узлами.

Для локальных имён без DNS можно задать оркестратору `AGENT_WS_HOST_IP`:
доступный агентам IPv4 адрес nginx (например, шлюз `docker_gwbridge` на одном
хосте). Он добавляется в `/etc/hosts` создаваемых Swarm-агентов для имени из
`AGENT_WS_URL`; имя TLS, проверка CA и SPKI-пины сохраняются. `127.0.0.1`
не подходит. В многоузловой установке адрес должен быть доступен с каждого
узла. Изменение настройки пересоздаёт управляемых агентов с новым сопоставлением.

`ssh-high-interaction/1` использует доверенный SSH-шлюз с Docker socket и отдельные
контейнеры на соединение без socket, секретов и сети. Запись терминала и
SFTP-файлов сохраняется снаружи среды. Шлюз размещается на manager-узле.
См. [настройку, запись и ограничения SSH](../../api/13-high-interaction.md).

Для нескольких хостов присоедините их к Swarm. Образы должны быть доступны на
каждом узле: задайте `DECOY_TCP_IMAGE`, `DECOY_REDIS_IMAGE` и `DECOY_HONEYTOKEN_IMAGE` как теги вашего
реестра и опубликуйте собранные образы. API и Redis остаются на основном хосте,
а агенты подключаются к ним через управляющую overlay-сеть. Каждый агент использует
Docker socket своего узла для локального контейнера приманки; образы должны быть
доступны на всех узлах. Доверенный SSH-шлюз по-прежнему размещается на manager-узле.

Операторские команды `stop` и `start` после первоначального автоматического
запуска остаются доступными. Изменение профиля требует явного `apply_config`.
Существующие ловушки остаются в ручном режиме. Выдача и отзыв реквизитов агента
для новых управляемых ловушек возвращают `409 agent_credentials_managed`.

Диагностика:

```sh
docker compose -f docker-compose.real.yml logs orchestrator
docker service ls --filter label=honeyforge.trap
docker service ps --no-trunc hf-trap-<TRAP_ID>
docker ps --filter label=honeyforge.worker=<TRAP_ID>
```

При обновлении старые сервисы без маркировки MASK-3 пересоздаются, а прежние
подключения API, Redis и nginx к decoy-сети удаляются. Пересоздание прерывает
активные сеансы приманок. Контейнеры-приманки останавливаются при потере агента
даже без новых событий; повторный запуск удаляет оставшийся контейнер только
по принадлежащей этой ловушке метке.
