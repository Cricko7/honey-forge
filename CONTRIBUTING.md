# Стиль Go и порядок изменений

Работаем по [карте модулей](api/README.md) и
[договору интеграции](src/backend/docs/api/module-integration.md).
Сначала подключаем зависимости модуля, затем проверяем его в общей сборке.
Новые маршруты регистрируются в `internal/app` и описываются в `api/openapi.yaml`.

- Импорты разделены на стандартную библиотеку, внешние зависимости и `honey-forge`.
- Между объявлениями функций и типов оставляем пустую строку. Большие структуры
  и таблицы ошибок записываем по одному полю/элементу на строку.
- DTO и бизнес-правила остаются у владельца модуля. HTTP, service и SQL имеют
  отдельные обязанности; общая сборка явно передаёт зависимости.
- Для изменения поведения сначала добавляем падающий тест. При форматировании
  и рефакторинге проверяем существующие сценарии, не меняя HTTP-контракт.
- Конфликт `config`/`clear_secret_fields` остаётся 422; SQL-миграции сохраняют
  опубликованные имена и порядок Goose.

Форматирование с закреплённой версией goimports, из корня репозитория:

```powershell
./scripts/format.ps1
./scripts/format.ps1 -Check
Set-Location src/backend
go fmt ./...
go vet ./...
go test ./...
go build ./...
```

С отдельной тестовой PostgreSQL БД в `TEST_DATABASE_URL`:

```powershell
go test -tags=integration ./... -count=1
go test -race -tags=integration ./... -count=1
```

На Windows для race нужен C-компилятор и `CGO_ENABLED=1`. Без
`TEST_DATABASE_URL` SQL-тесты пропускаются; это не проверка интеграции с БД.
