# Medium-ловушка Redis

`redis-emulator/1` сохраняет прежний идентификатор профилей, но запускает настоящий
Redis 7.4.6 в существующем изолированном worker-контейнере. Прозрачный перехватчик
передаёт исходные запросы и ответы без эмуляции; доступны RESP2, RESP3, Lua,
транзакции, Pub/Sub и обычные типы данных Redis. Аутентификацию проверяет Redis.

Каждый запуск автоматически создаёт случайные синтетические данные интернет-магазина:
12–32 пользователя, сессии с TTL и случайными идентификаторами, товары, заказы,
настройки, рейтинг товаров и поток событий. Имена, цены, остатки, даты и статусы
случайны; ссылки на пользователей и товары и суммы заказов согласованы.
Адреса используют домен `.example`. Данные общие для подключений к одной ловушке
и исчезают при остановке; при новом запуске создаётся новый набор.

Redis слушает только приватный Unix-сокет; сетевой порт принадлежит перехватчику.
Исходящие соединения и DNS блокирует существующий firewall. Нет host-монтов,
постоянных томов, Docker-сокета или серверных ключей. Сокет находится в tmpfs,
процессы работают под UID 65532 без эффективных capabilities. Телеметрия выходит
через TLS по stdin/stdout к доверенному агенту, затем через его журнал и WSS на сервер.
Неизменяемый опубликованный дескриптор каталога оставлен для совместимости.

## Профиль и запуск

Создайте профиль через тот же `POST /api/profiles`, что и для `tcp-banner`:

```json
{
  "request_id": "<UUID>",
  "name": "Redis medium",
  "description": "Интерактивная Redis-приманка",
  "type_id": "redis-emulator",
  "type_version": 1,
  "config": {
    "services": [{"name": "redis", "port": 6380, "password": "bait-pass"}],
    "management": {"heartbeat_interval_seconds": 5, "telemetry_flush_interval_ms": 100}
  }
}
```

`password` — учётные данные приманки. Поле `writeOnly`: в ответах профиля
значение скрыто, а агент получает полный snapshot. Затем создайте Trap, выдайте
реквизиты и отправьте команды
`apply_config` с `{"profile_revision":1}` и `start` с `{}` по шагам в
[руководстве агента](../../agent/README.md). `stop` тоже принимает `{}`.

Соберите единый агент из `src/backend` командой
`go build -o edge-worker.exe ./cmd/agent` (Linux: `go build -o edge-worker ./cmd/agent`). Запускайте
его с теми же `AGENT_WS_URL`, `AGENT_TRAP_ID`, `AGENT_TOKEN`,
`AGENT_REDIS_URL` и, при собственном CA, `AGENT_CA_FILE`, что и TCP-агент.
Для этой ловушки нужен собственный Trap ID и токен; Redis хранит её журнал
в отдельном ключе. Приложение
само запускает дочерний процесс Redis после команды `start`.

После `start` подключитесь к порту 6380 на хосте агента. Например, через
`redis-cli -h <хост> -p 6380` последовательно введите `AUTH bait-pass`,
`KEYS *`, `GET app:mode`, `SET demo value`, `GET demo`, `DEL demo`, `QUIT`.
Ответы отражают изменения общей базы этой ловушки.

Ловушка фиксирует `service.connection_opened`, каждый `service.auth_attempt`,
каждую `service.action` и `service.connection_closed`. События содержат
source IP/port, destination port, время, session_id/sequence, введённые
логин/пароль (включая `HELLO ... AUTH`), текст команды, объём принятого запроса, длительность
и причину завершения. События идут через тот же локальный журнал и WSS-канал
агента, что и TCP-баннер; читать их можно через `GET /api/events?trap_id=...`.
Журнал содержит введённые атакующим пароли и команды, поэтому храните его в
закрытом каталоге вне репозитория.

Лимит — 64 одновременные сессии и 30 секунд простоя входящих запросов.
Redis ограничен 32 МиБ данных с политикой `noeviction`, контейнер — 128 МиБ.
Большие и бинарные значения передаются полностью. Текст события ограничен
4096 байтами, AUTH-поля — 1024, `received_bytes` одного события — 8192;
при усечении выставляется `truncated`, итоговый `bytes_received` не ограничен.
Обычные запросы сопоставляются с ответами: `outcome` равен `accepted` либо
`rejected`, включая отказ `WRONGPASS`. Каждый ответ дополнительно сохраняется
как `service.action` с `action_kind=request` и префиксом `Redis response: `.
Это сохраняет существующую схему каталога; интерфейс показывает «Ответ Redis».
Pub/Sub, MONITOR, репликация и CLIENT REPLY переключают сессию в режим
раздельного наблюдения запросов и ответов: запросы имеют `unknown`, ответы
сохраняются отдельно. RESP3 push и атрибуты не расходуют очередь запросов.
При более чем 128 ожидающих запросах/ответах сопоставление также отключается,
чтобы ограничить память. Нетипичные кадры продолжают передаваться и записываются
блоками без предположений об успехе. Клиент получает исходные байты без изменений.
Для больших ответов сохраняется ограниченный образец с `truncated=true`.

Из `src/backend` выполните `go test ./internal/decoys/redistrap`.
Проверки реального runtime требуют `redis-server` в PATH; без него они пропускаются.
Контейнерная проверка `TestRealRedisDockerIsolationAndTelemetry` запускается с
`TEST_MASK3_DOCKER=1`, `DECOY_REDIS_IMAGE=honeyforge/redis-decoy:local` и тегом
`integration`; проверяет firewall, DNS, права, перезапуск, бинарные значения,
Lua, Pub/Sub и события в журнале агента.
