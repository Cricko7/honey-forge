# Профили

Реализация `docs/api/04-profiles.md` с правилами `01-common.md`. Модуль подключён в `internal/app`; настоящая cookie-сессия и CSRF берутся из auth.

## Что работает

- POST/GET `/api/profiles`, GET/PATCH/DELETE `/api/profiles/{id}`; коллекция поддерживает `limit`, `cursor`, `type_id`.
- POST сохраняет request_id на весь срок жизни организации. Повтор возвращает первоначальную revision; после удаления — `request_already_used`. Replay и no-op PATCH не создают дополнительный аудит/уведомления.
- PATCH/DELETE требуют один точный If-Match. Блокировка строки, проверка revision, изменение, снимок, аудит и уведомления находятся в одной транзакции. PATCH не создаёт команд и не меняет ловушки.
- PATCH config заменяет несекретные поля, сохраняет пропущенные writeOnly-значения и применяет clear_secret_fields. Проверяется полный эффективный config, включая required и предел 128 KiB. Ответы и списки скрывают секреты; исторические снимки сохраняют их.
- Viewer читает; изменяет только admin. Чужие/удалённые профили возвращают 404. Удаление сохраняет revision, request_id, аудит и историю.
- Строгий JSON и размер тела общие с auth: неизвестные/повторные ключи, неверный тип/null оболочки, несколько документов — 400; ограничения — 422; тело свыше 256 KiB — 413.
- Cursor подписан и привязан к организации и фильтру. Граница sequence исключает новые записи из следующих страниц. После перезапуска API cursor недействителен: перечитать первую страницу.

## Зависимости и подключение

Интерфейсов соседних модулей нет. `Dependencies` содержит функции, которые тесты заменяют фейками. Единственный локальный интерфейс `store` нужен для тестового хранилища.

Корневой `internal/app/profile_catalog.go` связывает профили с immutable-каталогом 03. LookupType возвращает точную версию и CheckConfig; секреты перечисляются через общую Schema.PublicConfig, изменения применяются через Schema.MergeConfig. Окончательный config дополнительно проверяется каталогом. Отдельной TCP-схемы в profiles нет. У tcp-banner секретов нет; непустой clear_secret_fields запрещён.

`CheckLiveBindings` проверяет `traps(organization_id, profile_id, deleted_at)` внутри транзакции удаления. Пока таблицы traps нет, привязок нет. Если схема 05 отличается, передать свою функцию HasLiveBindings. Для гарантии отсутствия гонки 05 обязан вызвать ReadProfileForBinding в **той же pgx.Tx**, которая создаёт привязку: FOR SHARE держится до commit и конфликтует с DELETE/PATCH. Функция отвергает удалённый/чужой профиль. Сама реализация 05 в этот модуль не входит.

`CaptureProfile(ctx, tx, organizationID, profileID, revision)` проверяет текущую revision и возвращает полный Snapshot под той же блокировкой. Использовать из транзакции создания команды 06; устаревшая revision даёт profile_changed. `Service.ReadSnapshot` читает сохранённую revision, включая историю удалённого профиля. Полный snapshot содержит секреты и предназначен только для доверенного внутреннего вызова/агента; операторского HTTP-маршрута для него нет.

По умолчанию атомарные аудит/уведомления сохраняются в profile_audit/profile_changes. Аудит содержит снимок email/роли, profile_revision и changed_fields; уведомления — только profile_id/revision или audit_id. Config в эти записи не передаётся. Для общего журнала 07/10 использовать Repository.WithWriters: переданные функции должны писать в полученную pgx.Tx и не делать самостоятельный commit/сетевой send. Общий WSS и доставка этих записей требуют подключения следующих модулей.

## Миграция и проверки

Из корня репозитория `docker compose up -d postgres` запускает PostgreSQL. Общий app.Open автоматически применяет корневые Goose-миграции при запуске API, включая таблицы профилей.

```powershell
go fmt ./...
go vet ./...
go test ./...
go build ./...
# TEST_DATABASE_URL — отдельная тестовая БД; каждый тест создаёт собственную схему.
go test -tags=integration ./...
go test -race -tags=integration ./...
```

Unit/httptest используют фейки каталога, привязок и хранилища. Integration проверяет настоящий PostgreSQL: CRUD, snapshot/replay, параллельные request_id и PATCH, пагинацию, привязку против удаления и откат при отказе audit/change writer. Полный сценарий роутера проверяет регистрацию, cookie/CSRF, admin/viewer и чужую организацию без запуска API-процесса.
