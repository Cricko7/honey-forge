# Панель команды организации

Откройте **Админ-панель** в меню (`/app/admin`). Раздел доступен администраторам.
Он показывает участников своей организации, создателя, эффективное право управления
ловушками и статус активности. Приглашения и API-ключи доступны отдельной ссылкой.

## Права и границы

Только создатель организации с браузерной сессией администратора может выдавать и
отзывать `can_manage_traps` у наблюдателей. Роль остаётся `viewer`; повышение до
администратора и передача владения через этот API не предусмотрены. Администраторы
управляют ловушками по своей роли; их право нельзя отозвать этим переключателем.

Делегирование разрешает создание, изменение и удаление ловушек **во всей своей
организации**, а также команды `start`, `stop`, `apply_config` по готовому профилю.
Делегат не получает управление профилями, связями перенаправления трафика,
подключением серверов, приглашениями, API-ключами, учётными данными агентов или
составом команды. Запуск и остановка доступны в карточке ловушки.

Сервер заново читает эффективное разрешение из БД при каждом запросе; открытые
браузеры обновляют SessionView каждые 30 секунд и при возвращении на вкладку.
Отзыв запрещает следующие управляющие запросы. Уже авторизованный запрос или
принятая команда могут завершиться; отзыв права не останавливает ловушки.

## API

- `GET /api/organization/members?limit=50&cursor=<UUID>` — браузерная сессия admin,
  страницы по ID по возрастанию, максимум 100 участников. `creator` возвращается
  независимо от страницы. `next_cursor` — последний ID, либо null. Это живой
  список, не snapshot: новые регистрации видны при обновлении.
- `PATCH /api/organization/members/{id}/trap-permission` — браузерная сессия
  создателя, разрешённый Origin и CSRF. Тело:
  `{"can_manage_traps":true,"expected_revision":1}`. Успех — 204.
  Конкурентное изменение — 409 `permission_changed`; защищённый admin —
  409 `permission_protected`; чужой/отсутствующий участник — 404.
- `POST /api/session/presence` — браузерная сессия admin/viewer, Origin и CSRF,
  пустое тело. Успех — 204. Нельзя передать чужие user_id/session_id.

Неизвестные/повторённые query-поля, дополнительные JSON-поля и тела GET отклоняются.
Административные маршруты не принимают Bearer API-ключи, даже вместе с cookie.
Ответы имеют `Cache-Control: no-store`. DTO участников не содержат паролей, хешей,
cookie, CSRF, кода приглашения или идентификаторов сессий.

## Активность

Видимая вкладка авторизованного приложения отправляет сигнал каждые 30 секунд.
Запись сессии обновляется не чаще раза в 30 секунд, только по серверному времени,
без продления срока сессии. Пользователь «в сети», если хотя бы одна действующая
браузерная сессия сообщала активность в последние 90 секунд. Закрытие или скрытие
всех вкладок даёт «не в сети» после этого срока; список обновляется каждые 15 секунд.
Logout отзывает только текущую сессию, остальные продолжают учитываться.
Истёкшие/отозванные сессии и API-ключи не считаются активностью.

`last_seen_at` — последний сигнал среди действующих сессий, а не историческое
время входа. После завершения всех сессий он равен null.

## Хранение и аудит

Миграция `20261014000100_organization_admin.sql` добавляет создателя, независимое
право, версию права и время активности сессии. Создатель новой организации
записывается в транзакции регистрации. Составной внешний ключ запрещает создателя
из другой организации. Идентичность сохраняется после удаления старого аудита.

Старые организации восстанавливают создателя по `organization.created`; при
отсутствии записи используется единственный admin из прежнего регистрационного
контракта. При неоднозначности создатель остаётся null и делегирование запрещено:
оператор должен отдельно проверить исторического владельца, автоматического
назначения по сортировке или первому входу нет.

Изменение права, увеличение `permission_revision`, запись
`member.trap_management_granted` / `member.trap_management_revoked` и уведомление
аудита фиксируются атомарно. Аудит указывает инициатора и target user ID, без
секретов. При текущей версии повтор того же значения ничего не меняет и не
создаёт дублирующий аудит. Ошибка аудита откатывает право.
История доступна через существующий `/api/audit`, действует общий HISTORY_RETENTION.

Миграции применяет существующий composition root при запуске API. Для выпуска
нужно обновить backend и frontend вместе. В mock-режиме показан текущий демо-admin;
выдача прав требует подключённого сервера.

## Проверки

Unit/HTTP tests проверяют самовыдачу прав, CSRF, Bearer, подмену role, валидацию,
скрытие секретов, пагинацию, ошибки БД и обновление права у существующей сессии.
PostgreSQL integration tests проверяют конкурентную запись, откат при сбое аудита,
защищённого создателя/admin, изоляцию организаций, несколько браузеров, таймаут
активности и реальные операции с ловушками и командами после выдачи/отзыва права.
Frontend tests проверяют HTTP-контракт, разграничение ролей и экранирование email.

Принципы минимальных привилегий и проверок на каждом запросе:
[OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html).
Защита изменяющих запросов:
[OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

`go build ./...`, `go test -race ./...`, общий прогон с `-tags=integration`
на свежей локальной PostgreSQL с проверкой TLS, Up/Down/Up миграций и отдельный
