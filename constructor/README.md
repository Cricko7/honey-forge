# Конструктор ловушек HoneyForge

Конструктор встроен в общую панель и создаёт новые текстовые TCP-ловушки из блоков поведения. Готовые ловушки из общего списка можно добавлять на доску отдельно.

Запуск из корня проекта:

```powershell
docker compose up --build -d
```

Откройте https://localhost:8443, войдите в свою организацию и выберите «Конструктор ловушек».

## Сборка новой ловушки

1. Откройте палитру. Двойным кликом или перетаскиванием добавьте «TCP-вход».
2. Настройте имя сервиса и свободный порт.
3. Добавьте «Приветствие» и/или блоки «Запрос → ответ». Соедините выход `out` предыдущего блока со входом `in` следующего.
4. Правила проверяются по порядку. Срабатывает первое совпадение: `exact` — полная строка, `prefix` — начало строки, `contains` — подстрока, `any` — любая строка. Сравнение учитывает регистр. Входные запросы заканчиваются LF или CRLF.
5. Нажмите «Развернуть». Дождитесь фактического состояния `running`. Подключайтесь к указанным портам сервера платформы.
6. События соединения, входящих данных и завершения видны на доске и в общем разделе событий.

Можно создать несколько TCP-входов с разными именами и портами: они станут сервисами одной новой ловушки. Доступно до 16 портов, до 64 правил на сервис и до 4096 байт в запросе/ответе/приветствии. Приветствие необязательно; соединение можно закрыть после него или после конкретного ответа. Неподходящая под правила строка записывается как входящие данные, но ответа не получает. Захват входящих данных ограничен 4096 байтами на соединение. Время ожидания входящих данных — 30 секунд.

Примеры: собственная административная консоль, простые почтовые/FTP-подобные текстовые сервисы, сервис PING/PONG, баннер с немедленным закрытием, несколько ложных сервисов на разных портах. Это управляемые текстовые ответы; полноценные реализации SSH, TLS, HTTP, SMTP или бинарных протоколов таким графом не создаются.

## Изменение и хранение

Остановите ловушку, измените блоки и снова нажмите «Развернуть»: профиль обновится и новая конфигурация будет применена к той же ловушке. Повторный запуск неизменённой схемы не создаёт дубликаты. Состояние запуска берётся из общего API, события — только из реальной телеметрии.

Доски сохраняются в Docker-томе `constructor_data` отдельно для каждой организации. Используется текущая сессия оператора; изменения доступны администратору и защищены CSRF. Удаление доски удаляет только схему: созданная ловушка остаётся в общем списке. Дублирование доски создаёт независимую схему без привязки к созданной ловушке; перед её запуском выберите свободные порты.

## Проверки

```powershell
python -m unittest constructor.backend.test_integration
python constructor/test_live.py
```

Для локального запуска проверок установите `constructor/requirements.txt` и `constructor/requirements-test.txt`. Live-проверка требует работающий Compose-стек, создаёт отдельную тестовую организацию и многопортовую ловушку, проверяет ответы, события, поток доски и отсутствие дубликата, затем останавливает ловушку. Она остаётся в тестовой организации для проверки результата. TLS проверяется с CA локального стека.

## CI/CD

Общий workflow проверяет тесты Python, фронтенд и Go и собирает Docker-образ конструктора. Образ с тегом релиза включается в `images.tar.gz` вместе с API, оркестратором и образами ловушек. При развёртывании автоматически запускается сервис из `deploy/compose.constructor.yml`, устанавливается маршрут `/constructor/` на HTTPS-хосте панели и проверяются ответы 200 для интерфейса и 401 без сессии. Данные досок сохраняются между релизами.

Production-сценарий рассчитан на Linux и существующий HTTPS nginx/API на localhost:8443; маршрут устанавливается через образ конструктора с использованием уже доступного Docker, без Python на хосте и дополнительных команд sudo. Если HTTPS-хост панели не удаётся определить однозначно, развёртывание останавливается и запускает откат приложения. Новый сервис слушает только loopback; отдельно запускать Python или открывать порт 8077 операторам не требуется.
